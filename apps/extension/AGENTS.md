# AGENTS.md — apps/extension

The MV3 browser extension — the repo's **generic protocol client**. Read the root
`AGENTS.md` first; this file only covers what is specific to the extension.

Stack: **WXT** + **plain Svelte**. SvelteKit is not used here — no router, no SSR, no
`$app` imports. Svelte components are mounted directly.

**This app is UI and browser integration only.** Relay communication, mining, key
management and ranking live in `packages/client`, because other hosts consuming the
same package — including products outside this repo — use exactly the same logic.
Code written here that a non-extension host would also need is in the wrong package.

Beyond the x.com share surface, this app is where the protocol's identity lives for
the browser: it can hold an identity generated here, or import one generated by any
other client over the existing key-transfer envelope (`packages/protocol/SPEC.md`
§15) — nothing new needed at the protocol level for that. It is also the home of the
**compute worker** described below: talking to a local OpenAI-compatible endpoint
(Ollama, LM Studio, or a generic custom endpoint) so it can be reached as a worker on
the ElseWeb compute network, over the protocol primitives in `packages/protocol`
(delegation, work-proof, receipt) and `relay/`'s `/compute/*` transport
(relay/AGENTS.md).

## Entrypoints

WXT discovers entrypoints from the `entrypoints/` directory. Current shape (no
`content.js` yet — the x.com share surface described above is not built; only the
compute worker below is):

```
entrypoints/
  background.js        # MV3 service worker: the worker's poll-claim-execute tick
  popup/                # toolbar popup (Svelte): compact worker status/toggle
  options/              # settings: relay URL, provider, models, limits, identity
```

To add an entrypoint, add the file/directory under `entrypoints/` — do not hand-edit a
generated manifest. Matches and permissions are declared in the entrypoint definition or
`wxt.config.js`.

## Compute worker

The extension is a **worker**, not a scheduler — it polls, claims at most one job at a
time per tick, runs it, and stops. See root `AGENTS.md`'s compute-bridge direction for
what problem this solves and relay/AGENTS.md's "Compute transport" section for the
wire contract it talks to.

- `src/providers/openai-compatible.js` — one shared `LocalAIProvider`
  (`probe`/`listModels`/`generateText`/`testModel`) for Ollama, LM Studio and any
  custom endpoint, since all three speak the same OpenAI-compatible subset.
  `src/providers/presets.js` holds only the preset data (default ports); the provider
  code itself knows no provider names. `text.embed` is not implemented — only
  `text.generate` and `code.generate`, per the task's initial-capability scope.
- `src/worker/limits.js` — admission checks (capability, allowed model, input size,
  output tokens, concurrency), run before a request ever reaches the local provider.
  Defaults live here; Options can override them, never a silent hardcoded ceiling.
- `src/worker/job-runner.js` — runs exactly one already-claimed job: negotiates the
  WebRTC DataChannel (`@elseweb-app/client`'s `negotiateAsAnswerer`), receives the
  request, admits it, calls the provider, returns the result, and only then mints and
  submits the compute receipt (`signReceiptAsWorker`). A failure at any stage returns
  before a receipt is ever signed — a failed job cannot produce a successful receipt.
- `src/worker/background-worker.js` (`runWorkerTick`) — the one poll-claim-execute pass
  the background entrypoint's `chrome.alarms` handler calls. Pure and
  dependency-injected, so it is unit-tested (`test/background-worker.test.js`) without
  chrome.* or a real relay.
- `src/worker/settings.js` / `src/worker/history.js` — persisted worker configuration
  and **metadata-only** job history (time, capability, model, duration, usage,
  success/failure — never a prompt or a result). A job's prompt and result live only in
  memory for the duration of `runClaimedJob` and are never written to storage.
- `src/platform/permissions.js` — every local AI endpoint and relay URL is contacted
  only after `chrome.permissions.request()` succeeds for that exact origin, requested
  at the moment the local user configures it in Options. `wxt.config.js`'s
  `optional_host_permissions` lists what origins are *eligible* to be requested; nothing
  there is granted at install time.
- Owner identity (`createKeyStore`) and the worker's own keypair/delegation
  (`createWorkerIdentityStore`) both live in `@elseweb-app/client`, not here — every
  extension page constructs its own store instances against the same
  `chrome.storage.local` (via `src/lib/wiring.js`), which is what keeps popup, options
  and the background worker in sync without message-passing.

**MV3 service worker constraints apply in full** (see "Background service worker"
below): `runWorkerTick` re-reads settings and identity from storage on every call and
holds no module-level state, and `chrome.alarms` (not `setInterval`) drives the poll
loop, plus one immediate tick on start-up so a restart does not wait a full period.

## Content script rules

- **Mount into a shadow root.** Use WXT's shadow-root content-script UI helper. Nothing
  the extension renders may inherit or leak host styles.
- **Do not write into the host page.** Reading the DOM is fine. The only permitted
  mutation is attaching our own container to the anchor point an adapter reports.
- **Never touch the host site's own share/post flow.** Not its handlers, not its state,
  not its network calls.
- **x.com is a SPA.** The composer is destroyed and rebuilt on navigation and on modal
  open/close. A one-shot `querySelector` at script start is wrong. Use a
  `MutationObserver` and re-attach whenever the anchor disappears. Attaching twice is a
  bug — mark our container and check for it before mounting.
- **Selectors live in `packages/adapters`, never here.** This directory contains no
  site-specific strings. If you are writing `[data-testid=...]` in this package, it
  belongs in an adapter instead.
- If the adapter cannot find an anchor, fall back to the generic adapter and keep
  running. Do not throw out of the content script.

## Background service worker

MV3 workers are killed at any time. Therefore:

- No module-level mutable state. Anything that must survive goes to `storage`.
- No `setInterval` for scheduling; use alarms.
- Treat every wake-up as a cold start.

## Messaging

Content script <-> background messages are validated with schemas from
`packages/protocol` on both send and receive. An unrecognized or invalid message is
rejected and logged, never acted on.

## Sharing: proof of work and rejections

Publishing a share means mining proof-of-work first, per
`packages/protocol/SPEC.md`. Required difficulty is not ours to pick — read it from
the relay's policy document and its per-key endpoint, cache it, and never hardcode a
value.

- Mining MUST be cancellable and MUST show progress. Sharing is user-initiated, so a
  short wait is acceptable; a UI that appears to hang is not.
- Stop at a bounded effort and surface a clear error rather than spinning forever.
- Mine immediately before submitting. A mined payload goes stale — never stash one
  and resubmit it later.
- Handle every rejection code the spec defines, distinctly. `POW_INSUFFICIENT` is one
  re-mine at the returned difficulty; `QUOTA_EXCEEDED` is a wait and **not** a re-mine;
  `SIGNATURE_INVALID` and `SCHEMA_INVALID` are our bugs and must not be retried.
  A blind retry loop against a relay is the failure mode to avoid here.

## Rendering: a flood only works if it is displayed

The relay bounds what it returns, and we bound it again. Neither side relies on the
other.

- Never render shares in raw chronological order.
- Cap how many shares a page renders.
- Enforce author diversity: one `pubkey` cannot dominate a page's view.
- Rank with key tier and age, engagement, and recency, so an unknown key with no
  engagement sorts to the bottom.

## Keys and device transfer

The user's persistent key is generated client-side, **extractable**, and never leaves
the device except through an explicit user-initiated transfer.

Transfer moves one identity between the extension, the site and mobile, in either
direction: the source shows a QR holding an encrypted envelope, the target scans it and
the user types a transfer code shown only on the source. The code is generated by the
client and high-entropy — never a short PIN, because a photograph of the QR is enough to
attack the envelope offline where expiry protects nothing. The private key never goes to
a relay, encrypted or not.

Warn plainly: whoever captures both the QR and the code owns that identity for good. A
key cannot be rotated without losing everything accrued to it.
Ephemeral-mode shares use a single-use key. Ephemeral mode is a privacy valve, not a
security control — a relay cannot tell an ephemeral key from a brand-new persistent
one, so never build a guarantee on it.

A persistent key lets a relay link all of a user's shares together. Say so in the UI.
That cost was chosen deliberately; it is not to be quietly imposed.

## Configuration

The user configures a **set** of relays, held in `storage` and editable at any time.
Never a literal in this package. With no relay configured the extension surfaces that
state rather than silently falling back to a built-in default.

The extension supplies `packages/client` with its storage port — `chrome.storage` lives
here and nowhere else.

## Bundle budget

The content script runs on every page the user visits. Keep it small; treat growth as a
regression. Popup and options bundles are less constrained but still not a dumping
ground. Adding a dependency to this package requires approval (root `AGENTS.md`, §7).

## Manual verification

There is no automated E2E for the extension in the MVP. After a change, load the dev
build in Chrome and confirm:

1. On x.com, the share control appears next to the composer.
2. Navigate within x.com (home -> profile -> back) — the control is still there, exactly
   once.
3. Open the composer in modal form — the control appears there too.
4. Share a piece of content, and confirm in the Network tab that **no request carrying
   that content goes to x.com** — only to the configured relay.
5. Content shared by another user appears on the same page.
6. On a site with no adapter, the extension loads and the generic fallback behaves.

For the compute worker specifically (unit tests cover the logic — see
`apps/extension/test` — this covers what only a real browser/local model can prove):

1. With Ollama or LM Studio running locally, Options detects it via a preset button,
   the permission prompt appears, and models list after granting it.
2. "Test" against an allowed model actually returns text, not just a model name in the
   list.
3. Turning the worker on with no relay URL, no provider, or no allowed models
   configured does nothing (the popup toggle stays disabled or a tick no-ops) rather
   than erroring.
4. A job run to completion appears in the popup's job counter and in local history with
   metadata only — open the storage in devtools and confirm no prompt/result text is
   present anywhere in `elseweb.worker-history`.
5. Killing and restarting the extension's service worker (chrome://serviceworker-internals
   or just reloading the extension) does not lose the worker identity or its delegation —
   both are read back from `chrome.storage.local` on the next tick.
