# Running a relay

This is an operator's guide to running an ElseWeb relay: what it does, what it does
not do, how to run one for development with no Supabase account at all, and how to
deploy the reference binding to Supabase edge functions.

If anything here conflicts with `packages/protocol/SPEC.md`, the spec is normative —
this document explains and points at real files; it does not redefine anything.

## 1. What a relay is, and is not

A relay stores events and serves them back under its own policy. That is the whole
job:

- It accepts a `POST /events` submission if the event passes the eleven verification
  steps of `SPEC.md` section 4, and rejects it with a typed error otherwise.
- It answers page, vote and feed queries by reading back what it has stored, bounded
  and diversified per author (`SPEC.md` sections 10 and 14).
- It publishes a machine-readable policy document at `GET /policy` describing its own
  rules, so a client can adapt instead of guessing.

A relay does **not**:

- issue identities — a keypair is generated by a client, never by a relay
  (`SPEC.md` section 9; non-negotiable 5 in the root `AGENTS.md`);
- speak for the network — rejecting a key is a decision local to this relay, not a
  network-wide ban. The same key can publish to any other relay in a client's set
  without friction;
- privilege itself — the reference relay in this repository is a relay like any
  other. It happens to also issue the `membership` attestation that gates ElseWeb's
  own feed (`relay/AGENTS.md`, "Membership issuer"), but that issuer is not
  implemented yet (no signing key, no issuance endpoint exists in this codebase as of
  this writing), and any third party can verify the claim shape and run a different
  issuer with a different trusted-issuer list.

The relay core lives in `relay/src/` as plain JS using only the Web-standard
`Request`/`Response` globals — no Supabase import anywhere in that directory. The
Supabase binding in `relay/supabase/` is one way to run that core, not the core
itself. See `relay/AGENTS.md` for the boundary this repository enforces between the
two.

## 3. Running without Supabase

The fastest honest path to a working relay is the one the test suite already proves
works: the relay core plus an in-memory storage port plus a thin `node:http` bridge.
No Supabase account, no Docker, no network dependency.

`relay/test/memory-store.js` implements the seven-method storage port from
`relay/src/store.js` entirely with `Map`s. `relay/test/http-server.js` bridges
Node's `http` server to the Web-standard `Request`/`Response` the core speaks. Wiring
them together is what `relay/test/e2e.test.js` does for every test in that file, and
it is short enough to copy directly:

```js
// run-relay.js
import { createRelayApp } from './relay/src/index.js'
import { createMemoryStore } from './relay/test/memory-store.js'
import { startRelayServer } from './relay/test/http-server.js'

const config = {
  protocolVersions: [1],
  kinds: ['share', 'reply', 'vote'],
  freshnessWindowSeconds: 300,
  maxPayloadBytes: 8192,
  quotaWindowSeconds: 86400,
  pow: {
    maxDifficulty: 24,
    challengeRequired: false,
    tiers: [
      {
        minAgeSeconds: 0,
        difficulty: { share: 4, reply: 4, vote: 2 },
        quota: { perKeyPerDay: 50, perKeyPerPagePerDay: 5, perKeyPerDayByKind: { vote: 200 } },
      },
    ],
  },
  attestations: { requiredFor: [], trustedIssuers: [], feedRequires: [] },
  listing: { maxEvents: 50, maxPerAuthor: 5, candidatePoolSize: 500 },
  feed: { maxEvents: 50, maxPerAuthor: 5, candidatePoolSize: 500 },
}

const app = createRelayApp({
  store: createMemoryStore(),
  config,
  clock: { now: () => Math.floor(Date.now() / 1000) },
})

const server = await startRelayServer(app)
console.log('relay listening at', server.url)
```

Run it with `node run-relay.js` from the repository root. This was run against the
current codebase while writing this document and produced a working relay on an
ephemeral port, verified with the `curl` commands in section 8 below.

The config shape is documented in the header comment of `relay/src/policy.js`; every
threshold shown above is illustrative, the same numbers `relay/test/fixtures.js`
uses to keep tests fast, not a production policy.

**This loses everything on restart.** `createMemoryStore` keeps events, key records
and quota counters in process memory with no persistence at all — the moment the
process exits, the relay's entire history is gone. Use this for local development,
for conformance-testing a client against a real HTTP relay, or for CI. Do not point
real users at it.

## 4. Installation

```
pnpm install
pnpm test
pnpm lint
pnpm build
```

These are the actual root scripts in `package.json`; there is no
`pnpm --filter relay dev` and none is documented here because it does not exist. All
four commands above were run against this repository while writing this document:
`pnpm test` passed 368 tests across 27 files (including `relay/test/e2e.test.js`,
`relay/test/verify.test.js`, `relay/test/policy.test.js`, `relay/test/quotas.test.js`
and `relay/test/feed.test.js`), `pnpm lint` and `pnpm build` both passed clean.

while iterating, pass a path the way you would to `vitest` directly:
`pnpm test relay` (this also picks up `packages/client/test/relay.test.js`, since
`vitest` matches on the substring "relay" in the file path).

## 5. Environment

These are every environment variable read by
`relay/supabase/functions/relay/index.js`, in the order `readConfig()` reads them.
Every one is required — the function calls `requireEnvironment()` / `integerFrom()`
for each and throws on startup if any is missing, so there are no silent defaults to
fall back on. `relay/supabase/.env.example` in this repository carries the same list
with realistic non-secret placeholder values and the two secrets left blank.

### Supabase project

| Variable | Required | Example | Secret | Purpose |
|---|---|---|---|---|
| `SUPABASE_URL` | yes | `https://abcxyz.supabase.co` | no | Project URL, used to build the service-role client |
| `SUPABASE_SERVICE_ROLE_KEY` | yes | — | **yes** | Server-side database access. Bypasses RLS. Must never appear in client code, a build artifact, a log line, or this repository |

### Verification limits (`SPEC.md` section 4)

| Variable | Required | Example | Secret | Purpose |
|---|---|---|---|---|
| `ELSEWEB_FRESHNESS_WINDOW_SECONDS` | yes | `300` | no | How far an event's `created_at` may be from server time, in either direction |
| `ELSEWEB_MAX_PAYLOAD_BYTES` | yes | `8192` | no | Encoded event size cap |
| `ELSEWEB_POW_MAX_DIFFICULTY` | yes | `24` | no | Ceiling this relay advertises as `policy.pow.max_difficulty` |

### Tiers

the established tier once it is at least `ELSEWEB_TIER_ESTABLISHED_AFTER_SECONDS`
old **and** has a clean record — any abuse report holds a key at baseline regardless
of age (`resolveTier` in `relay/src/policy.js`).

| Variable | Required | Example | Secret | Purpose |
|---|---|---|---|---|
| `ELSEWEB_TIER_ESTABLISHED_AFTER_SECONDS` | yes | `604800` | no | Age (seconds) at which a clean key reaches the established tier |
| `ELSEWEB_POW_DIFFICULTY_SHARE` | yes | `20` | no | Required difficulty for a `share` from a baseline key |
| `ELSEWEB_POW_DIFFICULTY_REPLY` | yes | `18` | no | Same, for `reply` |
| `ELSEWEB_POW_DIFFICULTY_VOTE` | yes | `14` | no | Same, for `vote` |
| `ELSEWEB_POW_DIFFICULTY_SHARE_ESTABLISHED` | yes | `14` | no | Required difficulty for a `share` from an established key |
| `ELSEWEB_POW_DIFFICULTY_REPLY_ESTABLISHED` | yes | `12` | no | Same, for `reply` |
| `ELSEWEB_POW_DIFFICULTY_VOTE_ESTABLISHED` | yes | `8` | no | Same, for `vote` |
| `ELSEWEB_QUOTA_WINDOW_SECONDS` | yes | `86400` | no | Rolling window quotas are counted over |
| `ELSEWEB_QUOTA_PER_KEY_PER_DAY` | yes | `20` | no | Baseline tier: total events per key per window |
| `ELSEWEB_QUOTA_PER_KEY_PER_PAGE_PER_DAY` | yes | `3` | no | Baseline tier: events per (key, page) per window — the bound that actually stops a flood |
| `ELSEWEB_QUOTA_PER_KEY_PER_DAY_VOTE` | yes | `50` | no | Baseline tier: vote-specific cap per key per window |

| `ELSEWEB_QUOTA_PER_KEY_PER_PAGE_PER_DAY_ESTABLISHED` | yes | `20` | no | " |
| `ELSEWEB_QUOTA_PER_KEY_PER_DAY_VOTE_ESTABLISHED` | yes | `500` | no | " |

### Attestations and listings

| Variable | Required | Example | Secret | Purpose |
|---|---|---|---|---|
| `ELSEWEB_TRUSTED_ISSUERS` | yes (may be empty string) | `` | no | Comma-separated hex pubkeys this relay trusts to sign attestations. Empty trusts nobody |
| `ELSEWEB_ATTESTATIONS_REQUIRED_FOR` | yes (may be empty) | `` | no | Comma-separated event kinds that require a verified attestation to publish at all |
| `ELSEWEB_FEED_REQUIRES` | yes (may be empty) | `` | no | Comma-separated claims an event must carry to appear in `GET /feed` |
| `ELSEWEB_LISTING_MAX_EVENTS` | yes | `50` | no | Max events returned by a page/vote query after diversification |
| `ELSEWEB_LISTING_MAX_PER_AUTHOR` | yes | `5` | no | Max events from one author in a page/vote query |
| `ELSEWEB_LISTING_CANDIDATE_POOL` | yes | `500` | no | Rows fetched from storage before diversification narrows them |
| `ELSEWEB_FEED_MAX_EVENTS` | yes | `50` | no | Same as listing, for `GET /feed` |
| `ELSEWEB_FEED_MAX_PER_AUTHOR` | yes | `5` | no | " |
| `ELSEWEB_FEED_CANDIDATE_POOL` | yes | `500` | no | " |

`ELSEWEB_ATTESTATIONS_REQUIRED_FOR` accepting an empty string is a real quirk of
`listFrom()` in `index.js`: an unset or empty variable becomes `[]`, but the variable
still has to exist as an environment entry for `Deno.env.get` to be asked about it at
all — leave it present and blank rather than omitting it, matching
`relay/supabase/.env.example`.

`.env` files are never committed (root `AGENTS.md` section 8, `relay/AGENTS.md`
"Keys and secrets"). `relay/supabase/.env.example` is the template; copy it, fill in
the two Supabase values, and keep the copy out of git.

## 6. Storage setup (Supabase)

The Supabase binding maps the relay's seven-method storage port
(`relay/src/store.js`) onto Postgres. Everything Supabase-specific lives in
`relay/supabase/`; the core in `relay/src/` never imports it.

### Migrations

Three forward-only migrations under `relay/supabase/migrations/`, applied in order:

1. **`20260822000100_events.sql`** — creates `public.events`, one row per accepted
   event, keyed by its content-hash `id` (so re-storing the same id is a no-op, not a
   duplicate). Indexes support the page query, the anchor narrowing, vote recount by
   `target_id`, thread lookup by `root_id`, and per-author quota scans. RLS is
   enabled with exactly one policy: `events_public_read`, `for select using (true)`.
   There is deliberately **no** insert/update/delete policy — with RLS on and no
   policy, anon and authenticated are denied those verbs outright. Writes only ever
   happen through the edge function's `service_role` client, which bypasses RLS by
   design; that is the only path where the eleven-step verification in `SPEC.md`
   section 4 runs. An anon client that could `INSERT` directly would skip signature,
   proof-of-work and quota checks entirely.

2. **`20260822000200_key_records.sql`** — creates `public.key_records` (one row per
   pubkey ever seen: first-seen time, per-kind counts, abuse report count) and
   `public.quota_counters` (windowed counts, keyed by `(pubkey, page_id, kind,
   window_start)`, with a `NULL page_id` row for the per-key counter and a non-NULL
   one for the per-(key, page) counter). Both tables have RLS **enabled with no
   policies at all** — not even a read policy. `GET /keys/{pubkey}` answers out of
   this data, but only through the edge function, which returns the protocol's
   shape (`required_difficulty`, `remaining_quota`) rather than these columns. A
   direct read policy would hand an attacker their own report count and tier
   threshold to tune a flood against.

3. **`20260822000300_quota_functions.sql`** — creates two `SECURITY DEFINER`
   functions, `elseweb_record_event` and `elseweb_quota_usage`, which are how the
   edge function reads and writes the two RLS-locked tables above from inside one
   transaction (recording an event touches three counters and a key record; doing
   that as separate statements from the function would leave a window where an event
   is stored but not counted — the window a flood would find). `EXECUTE` on both is
   explicitly revoked from `public`, `anon` and `authenticated` and granted only to
   `service_role`. A `SECURITY DEFINER` function callable by anon would be a hole
   straight through the RLS the tables above were given.

Apply them with the Supabase CLI, after linking to a project:

```
supabase login
supabase link --project-ref <your-project-ref>
supabase db push
```

`supabase db push` applies any migration under `relay/supabase/migrations/` that has
not yet been applied to the linked project. Run it from `relay/supabase/` (or point
the CLI at that directory) since that is where this repository's `migrations/`
directory lives.

### Deploying the function

```
supabase functions deploy relay
```

run from `relay/supabase/functions/`'s parent so the CLI finds `functions/relay/`.
Set the environment variables from section 5 as function secrets first (via the
Supabase dashboard, or `supabase secrets set --env-file .env` pointed at your filled-in
copy of `.env.example`) — the function throws on cold start if any is missing.

The function itself, `relay/supabase/functions/relay/index.js`, is deliberately thin:
it reads environment into `config`, builds `createSupabaseStore(supabase)` from
`relay/supabase/store.js`, and hands every request to the same `createRelayApp` the
in-memory path in section 3 uses. If a protocol decision ever needs to live in that
file, that is a sign it is in the wrong place — per `relay/supabase/README.md`, the
contract lives in `relay/src`, and a rule enforced only in the edge function would be
a rule no other binding of this relay obeys.

## 7. Relay policy

Every threshold is configuration, injected as the `config` object documented in the
header comment of `relay/src/policy.js` — never a literal in `relay/src/`. In the
Supabase binding, that object is assembled entirely from the environment variables in
section 5; a relay running a different binding assembles the same shape however it
likes.

What you control, and where:

- **Proof-of-work difficulty, per kind and per tier** —
  `ELSEWEB_POW_DIFFICULTY_{SHARE,REPLY,VOTE}` for a baseline (unknown) key, and the
  `_ESTABLISHED` variants once a key ages past `ELSEWEB_TIER_ESTABLISHED_AFTER_SECONDS`
  with a clean record. `ELSEWEB_POW_MAX_DIFFICULTY` is a separate ceiling — the most
  this relay will ever advertise in `policy.pow.max_difficulty` — and is not itself
  enforced as a per-tier difficulty.
- **Quotas** — `ELSEWEB_QUOTA_WINDOW_SECONDS` sets the rolling window; within it,
  `ELSEWEB_QUOTA_PER_KEY_PER_DAY` caps total events per key, and
  `ELSEWEB_QUOTA_PER_KEY_PER_PAGE_PER_DAY` caps events per `(key, page)` pair — the
  bound that actually stops a flood, since content is page-scoped
  (`relay/AGENTS.md`, "Anti-flood"). `ELSEWEB_QUOTA_PER_KEY_PER_DAY_VOTE` is an
  additional per-kind cap layered on top for votes specifically. Each has an
  `_ESTABLISHED` counterpart.
- **Freshness window** — `ELSEWEB_FRESHNESS_WINDOW_SECONDS`. An event whose
  `created_at` falls outside `[now - window, now + window]` is rejected with
  `STALE_TIMESTAMP` before anything else about it is checked past schema
  validation.
- **Payload cap** — `ELSEWEB_MAX_PAYLOAD_BYTES`, checked against the JSON-encoded
  byte length of the whole event.
- **Trusted issuers** — `ELSEWEB_TRUSTED_ISSUERS`, a comma-separated list of hex
  pubkeys. Only an `issuer-signed` attestation (`SPEC.md` section 8.1) from one of
  these is treated as valid; an attestation from anyone else is not rejected, just
  ignored, mirroring the client-tolerance rule that lets new attestation types
  appear without a coordinated flag day.
- **`feed_requires`** — `ELSEWEB_FEED_REQUIRES`, the claims an event must carry (from
  a trusted issuer) to appear in this relay's `GET /feed`. This does not gate
  publishing — it only gates what this one relay chooses to surface in its own feed
  (`SPEC.md` section 13). Setting a claim here with no corresponding entry in
  `ELSEWEB_TRUSTED_ISSUERS` produces a feed that can never contain anything, since no
  attestation can ever verify.
- **`required_for`** — `ELSEWEB_ATTESTATIONS_REQUIRED_FOR`, the event kinds that
  require a verified attestation to be accepted at all (step 9 of the eleven-step
  pipeline, `SPEC.md` section 4). This does gate publishing.
- **Listing and feed bounds** — `ELSEWEB_LISTING_MAX_EVENTS` /
  `_MAX_PER_AUTHOR` / `_CANDIDATE_POOL` for page and vote queries, and the
  `ELSEWEB_FEED_*` equivalents for `GET /feed`. `CANDIDATE_POOL` is how many rows are
  pulled from storage before author diversification narrows them down to
  `MAX_EVENTS`, capped at `MAX_PER_AUTHOR` per pubkey (`diversifyByAuthor` in
  `relay/src/feed.js`). The feed gets its own bounds because page-scoping does not
  constrain it at all — a page query is naturally narrow, a feed is cross-page by
  definition (`relay/AGENTS.md`, "Anti-flood").

**The policy document must stay truthful.** `GET /policy` (built by `buildPolicy()`
in `relay/src/policy.js`) is the only way a client not written against your specific
deployment knows what to expect. `relay/AGENTS.md` calls a relay that serves a policy
it then contradicts a real bug, not a cosmetic one: if `/policy` advertises a
difficulty or quota, a client that mines to that difficulty and stays under that
quota must not then receive `POW_INSUFFICIENT` or `QUOTA_EXCEEDED`. Changing any of
the environment variables above changes what the deployed function must actually
enforce, so redeploy and re-check `/policy` together, not one before the other.

## 9. Publishing a test event

Do not hand-build a signature or mine a nonce by hand. `@elseweb/client` does both,
along with deriving the page identity and talking to your relay set. This mirrors
what `relay/test/e2e.test.js` does against the in-memory relay, adapted to talk to
any relay by URL:

```js
// publish-test-event.mjs
import { createElsewebClient } from '@elseweb/client'

function createMemoryIdentityStore() {
  const values = new Map()
  return {
    async get(key) { return values.get(key) },
    async set(key, value) { values.set(key, value) },
    async remove(key) { values.delete(key) },
  }
}

const client = createElsewebClient({
  relays: [process.argv[2]], // e.g. http://127.0.0.1:PORT, or your deployed function URL
  identityStore: createMemoryIdentityStore(), // a real host uses IndexedDB or chrome.storage
})

// A keypair is minted locally the first time it's needed. No email, no password.
const identity = await client.identity.getOrCreate()
console.log('identity:', identity.publicKey)

const { results } = await client.publishShare({
  pageUrl: 'https://example.com/hello',
  text: 'hello from RUNNING_A_RELAY.md',
})
console.log('publish results:', results)

const { threads } = await client.readPage('https://example.com/hello')
console.log('threads:', JSON.stringify(threads, null, 2))
```

Run with `node publish-test-event.mjs <relay-url>`. Against the in-memory relay from
section 3, this was run while writing this document and produced:

```
identity: dd4ecfc94c5e3877cc474bc67ff11bd0c3b80c8c11f4c372c0e075f9da5dfd35
publish results: [ { relay: 'http://127.0.0.1:PORT', ok: true, id: '0413cd63f6d8...' } ]
threads: [ { "share": { ... "content": { "text": "hello from RUNNING_A_RELAY.md" } }, "replies": [], "score": 0, "relays": [ "http://127.0.0.1:PORT" ] } ]
```

`publishShare` mines the event at the difficulty your relay's `/policy` currently
advertises, signs it with the locally-held identity, and submits it — this is the
only supported way to get a schema-valid, correctly-mined, correctly-signed event
onto a relay you don't control the internals of. Point `relays` at your deployed
Supabase function's URL to test a real deployment the same way.

## 10. Deployment

The only deployment target documented here is Supabase edge functions, because it is
the only binding this repository implements — the one at `relay/supabase/`, deployed
per section 6.

No Docker, Fly, Vercel or bare-server instructions are provided, because no such
binding exists in this codebase. That is not a protocol limitation: `relay/src/`
is plain JS built entirely on the Web-standard `Request`/`Response` globals and a
seven-method storage port (`relay/src/store.js`), with no Supabase import anywhere in
it. Anyone can write a new binding — a Postgres pool behind a plain Node HTTP server,
a SQLite file behind a Deno server, anything — by implementing that port and handing
requests to `createRelayApp()` from `relay/src/index.js`, the same function both the
Supabase edge function (`relay/supabase/functions/relay/index.js`) and the test
harness (`relay/test/http-server.js`) call. `relay/test/memory-store.js` is a
complete worked example of the port with no database behind it at all.

## 11. Operator security checklist

- `SUPABASE_SERVICE_ROLE_KEY` (and, when it exists, a membership issuer's signing
  key) never appears in client code, in a build artifact, in a log line, or in this
  repository. It lives only in the edge function's environment.
- Terminate TLS in front of any production deployment. A Supabase project's edge
  function URL is HTTPS by default; if you put anything in front of it, keep that
  true.
- Set quotas and proof-of-work difficulty to numbers you actually mean — `/policy`
  is a promise to every client that reads it (section 7). Do not ship the
  illustrative values in this document or in `relay/supabase/.env.example` to
  production without deciding they are right for your traffic.
- Watch storage growth. Events are immutable and content-addressed by design
  (`SPEC.md` section 3) — nothing in this codebase prunes, expires, or archives old
  rows. `public.events` grows without bound for as long as the relay accepts writes.
  Deciding what, if anything, to prune is entirely on you; there is no built-in
  retention policy to defer to.
- There is no admin or moderation UI in this codebase. `key_records.report_count`
  exists as a column and affects tier resolution (section 7), but nothing here
  writes to it — wiring up abuse reporting is also on you.
- You are responsible for what your relay carries. Running a relay means storing and
  serving whatever passes your own verification and policy; this repository enforces
  the protocol's checks, not judgment about content.
- `.env` files, and any file holding a real value for a variable in section 5, are
  never committed. `.env` and `.env.*` are already in the repository's root
  `.gitignore`.
